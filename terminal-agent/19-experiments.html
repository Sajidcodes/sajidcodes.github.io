Experiments

Two ideas that sound good on paper: retries and cheap-model routing. One did nothing measurable. The other saved 64% and cost 21 points.

EVALUATION RETRIES ROUTING BUILD LOG 2026-10-19
In short
  • Retries: 84.4% → 86.7%. Inside the noise, so I don't claim a gain.
  • Routing: cost per task −64%, pass rate 84.4% → 63.3%. Debugging tasks fell from 70% to 40%.
  • Both are off by default until I have evidence they help.

Method

  • Same 30 tasks, same code version (6e8df3a9), 3 runs each.
  • Change one thing at a time against the baseline: 84.4% ± 1.9%.
  • Report the mean and sample standard deviation, overall and per tier.

Experiment 1: Retries

Idea: when a command fails, add a short hint to the tool result (error class plus a suggestion). Allow 2 retries, then say the budget is used up. 

ta/bin/python evals/run_eval.py --repeats 3 --retry-policy on --label retries-on

What happened: recovery went up (48.7% → 57.1%) and there were fewer failed commands (117 → 98). But the pass rate moved by 2.3 points, which is about one standard deviation.

My read

Retries help the agent fix commands that fail loudly. They don't help with the failures that actually lose tasks, where every command succeeds and the result is still wrong (section 15). That would explain why recovery improved and the score didn't.

Experiment 2: Model Routing

Idea: use gpt-4o for the first step and right after any failure. Use gpt-4o-mini for everything else. In practice, 70% of calls went to the small model. 

ta/bin/python evals/run_eval.py --repeats 3 --routing on --label routing-on

What happened: cost per task fell from $0.0156 to $0.0056 (−64%). The pass rate fell 21 points. The damage was uneven: file tasks lost 17 points, debugging lost 30.

Hypothesis

My routing rule escalates to the big model only after a command fails. In debugging, the hard part is reasoning about the bug, and that often happens with no failed command to trigger the switch. The small model does the hardest thinking. A better rule would route on the task or the step type, not only on errors.

What I Take From This

  • A plausible feature isn't an improvement until it beats the noise.
  • Cost savings need a quality number next to them. "−64% cost" alone would have been misleading.
  • Per-tier results showed me where each change hurt. The overall average hid that.
