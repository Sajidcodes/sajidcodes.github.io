Future Work

Each direction here comes from a measured result, not from a wish list.

RESEARCH OPEN QUESTIONS BUILD LOG 2026-10-19
In short
  • Make the agent check its own work before it says "done".
  • Route by how hard a step is, not only by whether a command failed.
  • Measure safety on commands the validator was never tuned on.

How I Choose What to Work On

I work in a loop, not down the list of sections:

  1. Run a small set of tasks, 3 times.
  2. Read the traces of every failure.
  3. Add each new failure to the failure-mode list (section 15).
  4. Fix one failure mode.
  5. Run the same tasks again and compare against the baseline.
  6. Record the result in the experiments section (section 19), even when it's "no change".

A section on this site gets written when there's data for it, not before.

1. Verify Before "Done"

Evidence: one task failed 9 times out of 9. In every baseline run, the agent stopped and reported it was done. Retries didn't help, because no command ever failed (sections 15 and 19).

Direction: require the agent to re-run the task's own test, or an equivalent check, before it may stop. The open question is whether this lifts tier 3 (debugging) more than it costs in extra steps.

2. Smarter Routing

Evidence: error-triggered routing saved 64% but cut debugging from 70% to 40%.

Direction: pick the model by the kind of step (planning or diagnosing vs. running a known command), not only after a failure. Success means most of the cost saving at no more than a few points of pass rate.

3. Honest Safety Numbers

Evidence: v2's 98% catch rate is a dev-set score, because I tuned v2 on that set (section 25).

Direction: build a held-out set, written without looking at the validator, and report v2 on it. That number, not 98%, is the one that should go on a résumé.

4. Local Suite vs Benchmark

Question: does my 30-task suite predict benchmark performance? If a change helps locally but not on Terminal-Bench, the local suite is measuring the wrong thing. If the two agree, the cheap local suite can screen ideas before an expensive benchmark run.
