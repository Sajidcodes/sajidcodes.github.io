Improvements

Safety validator v1 → v2: from 60% to 98% catch rate, with no new false positives. And why I trust the 60% more.

SAFETY VALIDATOR EVALUATION BUILD LOG 2026-10-19
In short
  • I built a 100-command safety test set before changing the validator.
  • v2 blocks 49/50 dangerous commands, up from 30/50, and false positives went from 5/50 to 0/50.
  • I tuned v2 on that same set, so I label its numbers as dev-set numbers.

Why a Test Set First

"The validator blocks dangerous commands" isn't a claim I can check. "It blocks 49 of 50 and wrongly blocks 0 of 50" is. A safety layer has two ways to fail, and I measure both:

  • Catch rate: dangerous commands it blocks.
  • False-positive rate: safe commands it blocks. Section 15 shows why that matters just as much.

The Test Set

  • 50 dangerous commands, in obvious and disguised forms.
  • 50 safe lookalikes, chosen to trip a lazy rule: rm -rf build/, git clean -n, multi-line sed -i.bak.
  • 206 real commands: every line of every solution.sh in the suite. These are correct by construction, so any block is a false positive.

What Changed in v2

  • Git operations that destroy work (reset --hard, clean -f, checkout -- .) are blocked, and the message suggests git stash. A block that explains the safe option keeps the agent moving.
  • Token-level parsing instead of plain regex, so curl … | python3 -m json.tool and quoted text no longer look like "pipe to interpreter".
  • Context inside one command: it follows cd and NAME=value.
  • New categories: download-then-run, reading credential files, data exfiltration, base64-to-shell and fork bombs.
  • A false-positive fix: a sed script is no longer read as a file path.
Why I trust the v1 numbers more

I wrote the test set, then improved v2 until it passed. That makes v2's 98% a dev-set score: it shows how well v2 fits commands I already knew about. v1 never saw the set before it was tested, so its 60% is the closer estimate for commands nobody planned for.
